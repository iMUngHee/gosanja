# gosanja

gosanja is a Rust engine that builds a deterministic map of a codebase from compiler facts: definitions, containment, references and calls, each with its source position and origin. No language model takes part in the analysis. Start at `docs/ARCHITECTURE.md` for how it is cut, `docs/CONVENTIONS.md` for the rules a change has to keep, and `docs/research/README.md` for the evidence behind the design.

## Editing and verification

- The gate is `scripts/check.sh`: format check, clippy with `-D warnings`, tests, doctests and `cargo deny`, then the Go adapter's checks. Run it before calling a change done. For a change to code, also run `scripts/self-check.sh`, which maps the repository with gosanja itself before and after the change: read its report, fix what it shows (a layering edge, coupling between modules that should not know each other, a definition left with nothing referring to it, a gap kind that grew), and say in the handoff what remains and why; `docs/CONVENTIONS.md` describes each section. The tests read the indexes checked in under `fixtures/` and need no indexer.
- For an indexing change, add or use a small fixture with an expected fact and check the engine's output against it. A change in what a snapshot contains shows up in `fixtures/*/expected`; say why each difference is right. Try the engine with `cargo run -p gosanja -- index --scip fixtures/rust-basic/index.scip --root fixtures/rust-basic --out <dir outside the repository>` and `cargo run -p gosanja -- validate <dir> --root fixtures/rust-basic`.
- `spec/` is normative. A change to a document, its JSON Schema, the goldens and `CHANGELOG.md` go in one commit; the rules are in `spec/README.md`.
- The core (`crates/core`) knows no language and recovers nothing from source text. Language knowledge belongs in adapters, which are separate programs behind `spec/adapter-contract.md`. Finding installed adapters is the command line's job (`crates/cli/src/discover.rs`, described in `docs/adapters.md`); the core runs the one program it is given. Tests that run `gosanja` as a process build the child's environment themselves, so that nothing installed on the host can decide a result.
- The Go adapter (`adapters/go`) is a Go module of its own, outside the Cargo workspace. `scripts/check.sh` runs its version check, `gofmt -l`, `go vet`, `go test` and `go mod verify` offline; its tests run against the stub `scip-go` in `fixtures/stub-tools`, and the end-to-end ones build `gosanja` with cargo; `scripts/check-live.sh` runs the tests behind the `live` build tag, which need the real `scip-go`. `docs/adapters/go.md` says what the adapter does to the analysed module and what it does not.
- The Rust adapter (`adapters/rust`) depends on `gosanja-schema` and, outside its tests, never on the core. Its gate tests run against a stub indexer in `fixtures/stub-tools`; `scripts/check-live.sh` runs the ignored tests that need the real `rust-analyzer`. `docs/adapters/rust.md` says what the adapter guarantees about the analysed tree and what it does not.
- Never copy code, names or paths from a private project into a fixture, a test or a document.
- For changes under `docs/research/`, follow `.ai/rules/research.md`.
- Edit shared agent guidance in `.ai/PROJECT.md`. The root `AGENTS.md` points to it and `CLAUDE.md` imports the root file. Check the wiring with `cmp .ai/PROJECT.md AGENTS.md` and `cmp .ai/rules/research.md .claude/rules/research.md`.

## Versioning

Three versions move independently. The release is the workspace package version in the root `Cargo.toml` (semver) and governs the command line and the Rust API. The snapshot schema and the adapter contract are `major.minor` versions recorded in every manifest and specified under `spec/`; their compatibility rules and change classes are in `spec/README.md`. A change to either interface is recorded in `CHANGELOG.md` with what a reader or an adapter author has to do.

- For every workspace release, including patch releases, add a `diff (old -> new, tool-version: new)` entry to `docs/self-index-history.md`. Build Gosanja and its Rust adapter from the new release, use them to index both releases with the same toolchain and layers, validate both snapshots, and record the structural diff before tagging.
- Tag the final release commit on `main` with an annotated `vX.Y.Z` tag matching the workspace package version. Push the tag with the release and verify it resolves to that commit on the remote.
