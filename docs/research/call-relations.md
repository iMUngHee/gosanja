# Precise call relations and how to represent uncertainty — research record (2026-11-23)

Call-graph construction literature (CHA, RTA, VTA and empirical soundness studies),
practical routes for Rust, Go and TypeScript, existing vocabularies for certain versus
possible call edges, and prior art for per-function control-flow outlines.

Collected by a web-research agent on 2026-11-23. Sources are given as raw URLs. A statement
prefixed `Unverified:` was not confirmed on a page the researcher opened, and vendor or
author claims are reported as claims. Sources that could not be opened are named in the
report. The text is kept as the researcher wrote it.

## Report

Unreachable sources: ACM DL pages (403), ScienceDirect (403), blog.japaric.io (TLS cert mismatch), IEEE Xplore (empty page), EPFL Infoscience (429). For ACM papers I used Semantic Scholar API records instead, and those often omit the abstract.

### A. Literature
Foundations
- Dean, Grove, Chambers. "Optimization of OO Programs Using Static Class Hierarchy Analysis". ECOOP 1995. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1007/3-540-49538-X_5 . This is CHA. Go's cha doc states the consequence: CHA "may include spurious call edges for types that haven't been instantiated", but it is "sound to run on partial programs, such as libraries without a main" (https://pkg.go.dev/golang.org/x/tools/go/callgraph/cha). Your current "maybe → every impl" edge is CHA, so label it that way.
- Bacon, Sweeney. "Fast static analysis of C++ virtual function calls". OOPSLA 1996. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/236337.236371 . This is RTA: it restricts targets to types that are instantiated. Your LLVM-IR vtable step ("concrete type T is coerced to dyn Trait somewhere") is the Rust counterpart of RTA's instantiated-type set, and it needs entry points or a whole program to be meaningful.
- Sundaresan, Hendren, Razafimahefa, Vallée-Rai, Lam, Gagnon, Godin. "Practical virtual method call resolution for Java". OOPSLA 2000. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/353171.353189 . This is VTA, and Go's vta package cites it as its algorithm. VTA propagates types along assignments, so a call site gets only the types that can actually flow to its receiver.
- Tip, Palsberg. "Scalable propagation-based call graph construction algorithms". OOPSLA 2000, pp. 281-293. http://web.cs.ucla.edu/~palsberg/paper/oopsla00.pdf . From the abstract I read: algorithms differ by the number of sets used to approximate run-time values (CHA none, RTA one per program, 0-CFA one per expression, k-CFA several). "For detecting unreachable methods, the inexpensive RTA algorithm does almost as well as the seemingly more powerful algorithms". XTA gives the best trade-off for call sites with a single target. Consequence: for reachability, RTA-level precision is enough. Per-site precision is where VTA/XTA pays off.
- Steensgaard. "Points-to analysis in almost linear time". POPL 1996. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/237721.237727 . Unverified (not opened): Andersen, "Program Analysis and Specialization for the C Programming Language", DIKU PhD thesis, 1994. Both are background only. Rupta is the Rust instance of this family.

Empirical soundness/precision
- Murphy, Notkin, Griswold, Lan. "An empirical study of static call graph extractors". ACM TOSEM 7(2), 1998; an earlier version appeared at ICSE 1996 (the S2 record conflates the two). https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/279310.279314 . The abstract was elided, so I have no findings from it. Unverified: it found that extractors over the same C code disagree substantially.
- Lhoták. "Comparing call graphs". PASTE 2007. https://plg.uwaterloo.ca/~olhotak/pubs/paste07.pdf . Read directly: the ideal call graph is the union of dynamic call graphs over all executions. A static graph over-approximates it and a dynamic graph is a subset. One spurious edge can pull in an entire unused module ("Hello World": 2706 spurious methods, 15993 spurious edges). The paper's tool ranks edges by how much difference each causes. Consequence: store the provenance of each edge so a spurious one can be traced back to its source; a graph diff should be a first-class feature.
- Reif, Kübler, Eichberg, Mezini. "Systematic evaluation of the unsoundness of call graph construction algorithms for Java". SOAP@ISSTA/ECOOP 2018. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3236454.3236503 . Reif, Kübler, Eichberg, Helm, Mezini. "Judge". ISSTA 2019. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3293882.3330555 . Consequence: graphs built with the "same" algorithm (e.g. RTA) in different frameworks are not comparable, because support for language features differs. Keep a per-feature test corpus (dyn, fn pointers, closures, async, drop, generics across crates) that fingerprints what each indexer misses.
- Sui, Dietrich, Tahir, Fourtounis. "On the Recall of Static Call Graph Construction in Practice". ICSE 2020. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3377811.3380441 . Median recall was 0.884 against test-observed calls. Added precision had little effect on recall. The main misses were native code and VM-initiated calls, not reflection. Consequence: missing edges cluster at runtime/FFI boundaries (in your case: executors calling poll, drop glue, FFI). Model those boundaries explicitly.
- Helm et al. "Total Recall? How Good Are Static Call Graphs Really?". ISSTA 2024. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3650212.3652114 . Builds dynamic baselines with fuzzing because ground truth is rarely available. Consequence: if you ever add an "observed" evidence level, it needs fixed entry points and a defined input corpus to mean anything.
- Samhi, Just, Bissyandé, Ernst, Klein. "Call Graph Soundness in Android Static Analysis". ISSTA 2024 (arXiv 2407.07804). https://arxiv.org/abs/2407.07804 . The 13 tools missed 61% of dynamically executed methods on average. Quote: "A high level of precision in call graph construction is a synonym for a high level of unsoundness". Consequence: never collapse "pruned by a precise analysis" into "no edge". Keep the CHA superset available underneath.
- Zhong, Wold, Windmann. "Detecting Call Graph Unsoundness without Ground Truth". arXiv 2604.00885, Apr 2026. https://arxiv.org/html/2604.00885v1 . They use the expected precision orders (VTA ⪰ RTA ⪰ CHA) as metamorphic oracles and find violations, e.g. RTA resolves lambda edges that CHA omits. Cross-framework Jaccard similarity is 3.9-21%. Consequence: assert subset relations between your evidence tiers in CI, because violations reveal indexer bugs.
- Antal, Hegedűs, Tóth, Ferenc, Gyimóthy. "Static JavaScript Call Graphs: a Comparative Study". SCAM 2018, arXiv 2405.07206. https://arxiv.org/html/2405.07206v1 . ACG had 99% precision and 91% (relative) recall; ACG+TAJS 98%/99%; all five tools 74%/100%. Edges found by only one tool were mostly false. Consequence: agreement between independent sources is a usable evidence signal, while a single-source edge is weak.
- Cai, Zhang. "A Cocktail Approach to Practical Call Graph Construction" (Coral). PACMPL OOPSLA 2023. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3622833 . Cheap resolvers run first and expensive refinement only on the residue. Consequence: architect the pipeline as tiers that each resolve some sites and pass the rest down.
- Li, Wu, Zhang, Wang, Su, Liu. "Neuro-Symbolic Indirect-Call Analysis under Opaque Pointers" (Facet). arXiv 2609.33547 v4, Oct 2026. https://arxiv.org/abs/2609.33547 . Type-based indirect-call analysis (MLTA) relied on LLVM pointer types, which LLVM 17 removed with opaque pointers. Consequence: type-based resolution of indirect calls on LLVM IR is now structurally weak. This bears directly on your LLVM-IR choice.

Rust-specific
- Li, He, Gui, Chen, Xue. "A Context-Sensitive Pointer Analysis Framework for Rust and Its Application to Call Graph Construction" (Rupta). CC 2024, pp. 60-72, DOI 10.1145/3640537.3641574. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1145/3640537.3641574 (the ACM page returned 403) and https://github.com/rustanlys/rupta . It runs on MIR and mimics monomorphization. It finds 29% more edges than static-dispatch-only "Ruscg" and removes about 70% of the spurious dyn edges of RTA-based "Rurta". It is pinned to nightly-2024-02-03 with rustc-dev (https://raw.githubusercontent.com/rustanlys/rupta/main/rust-toolchain.toml). Consequence: Rupta gives the precision ladder for Rust (static < RTA < points-to). As a dependency it is a stale-nightly risk.
- Li, He, Chen, Xue. "Stack Filtering: Elevating Precision and Efficiency in Rust Pointer Analysis". CGO 2025. https://dongjiehe.github.io/publications.html . Unverified (from a search snippet): it seeds its call graph with RTA.
- Hejderup, Beller, Triantafyllou, Gousios. "Präzi: From Package-based to Call-based Dependency Networks". EMSE 2022, arXiv 2101.09563. https://arxiv.org/html/2101.09563 . They chose MIR over LLVM IR because in LLVM IR "call graph generators can only resolve monomorphized features", and used rust-callgraphs (MIR + CHA; https://github.com/ktrianta/rust-callgraphs) with no function-pointer support. Coverage was 70% of all indexed releases. Consequence: there is prior evidence that LLVM-IR call graphs for Rust were abandoned for MIR, although your debuginfo vtable names partly close the type gap they cite.
- Prior LLVM-IR tool: cargo-call-stack. https://github.com/japaric/cargo-call-stack/blob/main/README.md . It has "imperfect" fn-pointer and dyn support and matches indirect calls by LLVM signature. Since about nightly-2022-09-20 (opaque pointers) "there's no distinction between function pointers and trait objects at the llvm-ir". It needs fat LTO and nightly; last tested nightly is 2023-11-13. Its proposed fix, rustc eRFC #59412 (`-Z call-metadata` with `!{"dyn","Trait","method"}` on impls and dispatch sites), is still open; the implementing PR #59777 was closed. https://github.com/rust-lang/rust/issues/59412 . In that thread eddyb suggested deriving "dynamic call target sets" from MIR instead.
- Kani's reachability collector over rustc_public. https://raw.githubusercontent.com/model-checking/kani/main/kani-compiler/src/kani_middle/reachability.rs . It is a cross-crate mono collector. `PointerCoercion::Unsize` to dyn collects the vtable methods plus the destructor of the concrete type. `ReifyFnPointer`/`ClosureFnPointer` resolve through `Instance::resolve_for_fn_ptr`. `Drop` terminators resolve through `resolve_drop_in_place`. Edges carry a `CollectionReason`: DirectCall, IndirectCall, VTableMethod, Static, StaticDrop. It does not store call-site locations, although its visitor receives them, and it adds no edges at fn-pointer call sites. Consequence: a working precedent for exactly the facts you get from LLVM IR, built on a typed API with an evidence label on each edge.
- Unverified (search snippet only, ACM 403): VanHattum et al., "Verifying Dynamic Trait Objects in Rust", ICSE-SEIP 2022, reports dyn dispatch in 37% of the top-500 crates.

Go-specific
- I found no academic evaluation of Go call-graph precision; three searches returned only Java/Android work. The primary implementation evidence: commit 264b4b5 in x/tools by Z. Pavlinovic, 2024-08 (https://go.googlesource.com/tools/+/264b4b5b0d07552ebb4598c12b9d3871f69b83d7). It adds return-parameter nodes so the type propagation graph has F×(R+C) edges instead of R×F×C: "~5% time savings", and the graph is "~31% smaller" when the initial graph is CHA.
- govulncheck's actual construction (https://go.googlesource.com/vuln/+/0782b76014f15f24e22a438f30f308df42899ba1/internal/vulncheck/utils.go): `cha.CallGraph(prog)`, then forwardSlice from the entries, then `vta.CallGraph(fslice, initial)`, repeated once with the VTA graph as the base, then `DeleteSyntheticNodes()`. Its documented limits (https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck): "analyzes function pointer and interface calls conservatively" (possible false positives and inaccurate stacks); reflect calls are invisible (false negatives); "use of the unsafe package may result in false negatives".

JavaScript/TypeScript
- Feldthaus, Schäfer, Sridharan, Dolby, Tip. "Efficient construction of approximate call graphs for JavaScript IDE services" (ACG). ICSE 2013, pp. 752-761. https://api.semanticscholar.org/graph/v1/paper/DOI:10.1109/ICSE.2013.6606621 (abstract elided). Unverified: field-based flow analysis that ignores dynamic property access. In the Antal study it is the most precise tool (99%).
- Chakraborty, Gnanakumar, Sridharan, Møller. "Indirection-Bounded Call Graph Analysis". ECOOP 2024, LIPIcs 313, 10:1-10:22. https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ECOOP.2024.10 . Bounding indirection gives about 2x speed for about 5% recall loss. Edges found early tend to be correct.
- Jelly (cs-au-dk): https://github.com/cs-au-dk/jelly . Covers JS "(and TypeScript)" on Node.js, "intentionally not fully soundly". - Python, for the transferable lesson: Salis et al., "PyCG". ICSE 2021, arXiv 2103.00587. https://arxiv.org/abs/2103.00587 . Precision about 99.2%, recall about 69.9%. Lesson: a high-precision, lower-recall default is acceptable to users only if what is missing is made visible.

### B. Practical routes
Rust (LLVM IR)
1. Format coupling. LLVM policy (https://llvm.org/docs/DeveloperPolicy.html): "The textual format is not backwards compatible". Bitcode is readable "since version 3.0", but "Debug metadata is special in that it is currently dropped during upgrades". Reading rustc bitcode with a newer LLVM can therefore silently lose the debuginfo you depend on. Reading it with an older LLVM is not supported at all. rustc's LLVM moves often (https://doc.rust-lang.org/beta/releases.html): LLVM 22 in 1.95 (2026-04-16), LLVM 23 in 1.99 (2026-10-01). The llvm-ir crate is 0.11.3 (2025-02-21), supports LLVM 9-19, and keeps only debug locations, dropping other DI metadata (https://docs.rs/crate/llvm-ir/latest). It cannot read current rustc output and would lose your vtable DI names. Unverified (search only): inkwell supports LLVM 23 on master only. Verdict: a binding is not more robust. It swaps text-format drift for a hard dependency on the exact LLVM major version. If you stay on LLVM IR, keep parsing text, but only the small subset you need (call/invoke, DILocation incl. inlinedAt, DIGlobalVariable for vtables), and pin a golden-file test per rustc release.
2. Vtable names. PR #89597 (Rust 1.57) names vtables `<Type as Trait>::{vtable}`; before that all were "vtable" (https://github.com/rust-lang/rust/pull/89597). Unverified (search only): issue #1563 is still open, so vtable fields are not named by method, and mapping a vtable slot to a method needs offset arithmetic or the impl list.
3. Mangling. v0 is the default on stable since 1.97 (2026-07-09); legacy mangling is nightly-only and slated for removal (https://blog.rust-lang.org/2026/07/09/Rust-1.97.0/). Use rustc-demangle; v0 preserves generic arguments, which makes instance names more useful.
4. Inlining at -O0. Unverified (search snippets from RFC 3778 and an internals thread; no official doc opened): `#[inline(always)]` maps to `alwaysinline` and is applied even at opt-level 0. Expect missing call instructions for those callees and recover them from `inlinedAt` chains.
5. Async, closures, drop glue (Unverified; inferred from language semantics, not from a source). The caller of an `async fn` only constructs the future. The body runs from `poll`, which an executor reaches through a generic or dyn call. So the IR has "caller → constructor" but not "caller → body". Synthesize an `awaits` edge from MIR/SCIP structure. Drop glue appears as `drop_in_place::<T>` calls, which Kani labels StaticDrop/VTableMethod.
6. Generics. Unverified: with share-generics (on by default in debug builds) an instance may be codegen'd in an upstream crate only. Edges will point at bodies whose IR lives in another crate's output.
7. Alternative route: rustc_public. Status at https://github.com/rust-lang/goals/issues/266 : not published; reopened as a 2026 goal; 2026-10-30 update "No real progress in the last month". The crate doc says "not yet published and is still subject to breaking changes" (https://doc.rust-lang.org/nightly/nightly-rustc/rustc_public/index.html). The API has `Instance::resolve`, `resolve_closure`, `resolve_drop_in_place`, `resolve_for_fn_ptr` and a monomorphized `body()` (https://doc.rust-lang.org/nightly/nightly-rustc/rustc_public/mir/mono/struct.Instance.html). You build the mono collector yourself, as Kani did. It still needs nightly plus rustc-dev.

Go
- Loading: go/packages with `LoadAllSyntax` (NeedSyntax, NeedTypesInfo, NeedDeps) (https://pkg.go.dev/golang.org/x/tools/go/packages). `Tests: true` adds the variants "p [p.test]" and "p.test", so functions are duplicated across variants and must be deduplicated by source position.
- SSA: `ssautil.AllPackages(pkgs, ssa.InstantiateGenerics)` builds SSA for all deps; `Packages` builds only the initial ones (https://pkg.go.dev/golang.org/x/tools/go/ssa/ssautil). `MainPackages` may include synthetic testmain packages. `AllFunctions` is documented as not really linker-like (its TODO).
- Per call site (https://pkg.go.dev/golang.org/x/tools/go/ssa): `CallCommon.StaticCallee()` is non-nil for direct calls; `IsInvoke()` marks interface dispatch; call mode with a non-function value is a func-value call. `Go` and `Defer` carry a CallCommon, so spawn and defer are distinguishable.
- Conversion sites, i.e. the Go analogue of your vtable fact: `MakeInterface` "constructs an instance of an interface type from a value of a concrete type", e.g. `t2 = make Stringer <- t0`. Its Pos() is the Lparen only "if the instruction arose from an explicit conversion". Unverified: implicit conversions have no Pos of their own, so attribute them to the enclosing instruction or statement.
- Algorithms (https://pkg.go.dev/golang.org/x/tools/go/callgraph and subpackages): edges are (caller, site, callee) triples; built-ins are not in the graph; reflect.Value.Call has no Site. CHA needs only the program and is sound on libraries. RTA needs main/init roots of a complete program with all bodies and has no reflection edges. VTA refines an initial graph (CHA if nil) and is sound "modulo use of reflection and unsafe". It needs InstantiateGenerics and is "experimental" (https://pkg.go.dev/golang.org/x/tools/go/callgraph/vta). Its source TODO says the handling of generic bodies and instantiation wrappers still needs updating (https://github.com/golang/tools/blob/master/go/callgraph/vta/vta.go). Unverified: I found no cost numbers for mid-size codebases.

TypeScript
- Today's API is TS 6. TS's own call hierarchy (https://raw.githubusercontent.com/microsoft/TypeScript/release-5.9/src/services/callHierarchy.ts) uses `getSymbolAtLocation` plus aliases for outgoing calls and FindAllReferences for incoming calls. An interface method call resolves only to the signature. Calls inside anonymous callbacks are attributed to the enclosing named function. Passing `foo(bar)` is not a call of bar. `checker.getResolvedSignature` gives the overload-resolved declared target (https://ts-morph.com/navigation/type-checker).
- Cannot resolve: dynamic property access, values typed `any`, callbacks stored and called later. Use Jelly's flow-based edges as a separate evidence tier.
- TS 7 status:
  - typescript-go was archived 2026-09-01; its README still says API "not ready" (https://github.com/microsoft/typescript-go).
  - The 7.1 beta ships a new API with `typescript/sync` and `typescript/async`, `createProgram`, and snapshots (https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/). The post says it supports "type-checker and program APIs" but names no checker methods. Batch use does not load tsconfig itself. The RC is promised "in about a month".
  - npm dist-tags checked today (2026-11-23): latest 7.0.2, beta 7.1.0-beta, next 7.1.0-dev.20261123.1, no 7.1 RC tag (https://registry.npmjs.org/-/package/typescript/dist-tags). Unverified (secondary only): planned stable date 2026-11-24.

### C. Representing uncertainty
- No established cross-tool vocabulary exists. LSP CallHierarchyIncomingCall/OutgoingCall carry only from/to plus `fromRanges`, with no certainty or dispatch field (https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/). SCIP has no call-edge construct; `enclosing_range` is the suggested way to build call hierarchies (https://raw.githubusercontent.com/sourcegraph/scip/main/scip.proto).
- Prior art to borrow:
  - CodeQL separates `getTarget` (the static target) from `getARuntimeTarget`/`viableImpl` (viable targets). `exactCallable` is "a conservative analysis that returns a single callable", and `lowConfidenceDispatchTarget` covers "imprecise open-world type-based dispatch resolution" (https://raw.githubusercontent.com/github/codeql/main/java/ql/lib/semmle/code/java/dispatch/VirtualDispatch.qll).
  - Sourcetrail marks name/type-only post-processed edges "ambiguous" ("some of these edges may never be encountered") and draws undefined-but-used symbols as hatched "non-indexed" nodes (https://raw.githubusercontent.com/CoatiSoftware/Sourcetrail/master/DOCUMENTATION.md).
  - Kani labels edges DirectCall, IndirectCall, VTableMethod, Static, StaticDrop.
  - Go names each graph by its algorithm (static/cha/rta/vta). govulncheck shows one representative call stack per finding (`-show traces`) and admits that fn-pointer and interface calls are conservative.
  - Doop/WALA: I opened no primary docs. Unverified: Doop emits CallGraphEdge/Reachable relations plus statistics such as polymorphic call sites.
- Recommendation: give each edge two fields rather than inventing a confidence score.
  - `mechanism`: static | dyn-trait/interface | fn-pointer/func-value | closure | drop | spawn/defer | await/poll | macro-generated.
  - `resolution`: direct (one statically known instance) < mono-instantiated (resolved generic) < coercion-filtered (RTA-like: the type is converted to dyn/interface somewhere in the program; record the coercion site) < hierarchy (CHA: any implementor) < name-only (Sourcetrail-style ambiguous).
  - Optional refinements: `flow` (VTA/points-to) and `observed` (dynamic), kept as overlays.
  - Also mark call sites with no resolved target ("open"), the way Sourcetrail shows non-indexed nodes, so humans can see what is missing.
  - The algorithm names are standard and map onto these tiers. Test the subset relations between tiers.

### D. Control-flow outline
- Parsers: rust-analyzer's syntax crate (ra_ap_syntax) advertises "graceful handling of errors", "full-fidelity representation" and incremental reparsing. It is at 0.0.364, published 2026-11-23, so expect weekly breaking versions (https://docs.rs/ra_ap_syntax/latest/ra_ap_syntax/). Unverified, not opened: syn needs a well-formed token stream, which makes it less suited to code mid-edit. For Go, go/ast falls under the Go 1 compatibility promise. For TS: the TS AST, oxc, or swc. Tree-sitter gives one implementation for all three, but each grammar is a separate maintenance surface. Since you already depend on each language's toolchain, the native parsers give spans consistent with SCIP and the compiler. That last point is my inference.
- Comprehension evidence is thin:
  - Su et al., "Structure-Aware Rendering", arXiv 2609.24616, Sep 2026 (https://arxiv.org/html/2609.24616v1). With 53 participants, AST-first reveal changed gaze patterns, and participants subjectively reported better sense of structure. Quiz scores did not differ (ceiling effects).
  - Unverified (ScienceDirect 403; search snippet only): Hendrix et al., Science of Computer Programming 2005, found Control Structure Diagrams significantly improved comprehension.
  - I found no study of per-function nested outlines specifically.

### Implications
- Rust: The LLVM-IR choice is defensible for post-monomorphization edges, but sources argue it is the fragile layer: textual IR has no compatibility promise; rustc changed LLVM majors twice in 2026; bitcode upgrades drop debug metadata; bindings are pinned to a single LLVM major; Präzi moved to MIR; cargo-call-stack stalled on opaque pointers. Recommend a rustc_public driver modelled on Kani's collector as the target design. It gives the same facts (Unsize coercion sites, vtable methods, fn-pointer reification, drop glue, instances), typed and with MIR spans. Cost: a nightly pin plus rustc-dev until rustc_public reaches crates.io, which has no date ("no real progress" as of 2026-10-30). Keep LLVM IR as a pinned fallback/cross-check with per-release golden tests, and synthesize await edges in either path.
- Go: go/packages (LoadAllSyntax, Tests) → SSA with InstantiateGenerics → static edges from StaticCallee, coercion facts from MakeInterface, CHA then VTA sliced from entries (govulncheck's recipe). Maintenance cost is low: an official x/tools API, with VTA marked experimental. Label edges cha versus vta and report reflect and unsafe as open sites.
- TypeScript: Use the TS 6 checker now (getResolvedSignature plus implementations of interface methods as the CHA tier). Track the 7.1 API, which is still beta as of 2026-11-23. Add Jelly as an optional flow tier for JS-level edges. Cost: two compiler APIs during the migration window.
- Vocabulary, all languages: `mechanism` × `resolution` {direct, mono, coercion-filtered, hierarchy, name-only; refinements flow and observed}. Record evidence sites (the coercion or MakeInterface location) and mark open call sites.
